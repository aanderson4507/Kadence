# Team Setup: Database Access and Secrets

Every teammate runs their own local PostgreSQL. Credentials live only in a git-ignored `.env` file.
Architecture and schema details are in [database.md](database.md).

## What is and is not in git

| File | In git? | Contains |
|---|---|---|
| `.env.example` | Yes | Placeholders only (`YOUR_LOCAL_PASSWORD`) |
| `.env`, `.env.*` | **No** (git-ignored) | Your real `DATABASE_URL` |
| `prisma/seed.ts` | Yes | Demo account `demo` / `kadence-demo`, development only |
| `server/generated/prisma` | No | Generated by `npm install` |

## First-time setup (each teammate)

1. **Install PostgreSQL 17** (pick one):
   - Windows: `winget install PostgreSQL.PostgreSQL.17`
   - macOS: `brew install postgresql@17`
   - Docker: `docker run --name kadence-db -e POSTGRES_PASSWORD=<choose-a-password> -p 5432:5432 -d postgres:17`
2. **Create your `.env`:**
   ```sh
   cp .env.example .env        # Windows PowerShell: Copy-Item .env.example .env
   ```
   Open `.env` and replace `YOUR_LOCAL_PASSWORD` with the password you set for the `postgres` user.
   Use a password that is not reused anywhere else. This file never leaves your machine.
3. **Install, migrate, seed, verify:**
   ```sh
   npm install            # generates the Prisma client and enables the pre-commit secret check
   npm run db:migrate     # creates kadence_dev and applies migrations
   npm run db:seed        # loads demo data
   npm run db:check       # prints server version and row counts
   ```
4. **Run:** `npm run dev:api` and `npm run dev`. Health check: `http://localhost:5173/api/health`.

### Troubleshooting

| Symptom | Fix |
|---|---|
| `DATABASE_URL is not set` | `.env` is missing or not in the project root. Repeat step 2. |
| `password authentication failed` | The password in `.env` differs from the one set in PostgreSQL. |
| `ECONNREFUSED 5432` | PostgreSQL is not running. Start the service or the Docker container. |
| Password has `@ : / # ?` | URL-encode it (`@` becomes `%40`) or choose a simpler password. |

## Shared Neon cloud database

Used only to apply approved migrations, never for daily development.

- **Team lead:** create the Neon project, then create one database role per person (Neon console →
  Roles) so access can be revoked individually. Send each teammate their connection string through a
  private channel (direct message or password manager), never email threads, issues, PRs or public chat.
- **Teammate:** put the Neon URL in `.env` only for the moment you run `npm run db:deploy`, then switch
  back to the local URL. Never run `db:reset` or `db:migrate` against Neon.
- **Leaving the team or suspected leak:** the lead drops that role (or resets the password) in Neon.

## Keeping secrets out of git

- `.gitignore` excludes `.env`, `.env.*` (except `.env.example`), keys, certificates, credential JSON
  files and database dumps.
- `npm install` sets `core.hooksPath` to `.githooks`, and the pre-commit hook runs
  `scripts/check-secrets.mjs`. It blocks staged `.env` files, database URLs with real passwords, private
  keys and common API tokens. Run it manually with `npm run check:secrets`.
- Do not bypass the hook with `--no-verify`.
- Before opening a PR, check `git status` shows no `.env` file.

## If a secret is committed

Deleting the file in a new commit does **not** remove it from history.

1. Treat the credential as compromised and rotate it immediately (change the Postgres password, or reset
   the Neon role password).
2. Tell the team lead.
3. Only then, if needed, remove it from history (`git filter-repo`) and force-push with the team's
   agreement. Rotation is the part that actually protects you.
